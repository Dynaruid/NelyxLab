# Windows 창 크기 변경 추종과 래스터 위치

원문 `work7.md` · 작성 2026-11-26 KST · 후속 구현·검증 11-27 · Nelyx 기준 `14851cf0` · Doroti 비교 `35475819` · 보관 2026-11-28 KST · 원문 조회 `git show 92b34484:work7.md`

**기본 추종을 구현하고 Testbed 3의 왼쪽 위 드래그 순간 이동을 수정했다.** 전체 표시 성능과 물리 마우스 확인은 당시 남았다.

## 구현과 원인

- 브라우저 레이아웃이 CanvasKit의 새 버퍼보다 먼저 바뀌면서 기존 캔버스 픽셀이 축별로 늘어났다. SDK가 관리하는 메인·팝업 캔버스의 래스터 배율을 양축에서 고정하고 뷰포트로 자르도록 했다. 크기·DPR·여백을 한 세대로 게시하고 `resize`·`ResizeObserver`가 예약 프레임을 앞당길 수 있게 했다. 같은 배율의 CanvasKit 버퍼는 GPU·메모리 한도 내에서 여유 용량을 재사용한다.
- Windows 창별 `windowsRetainedViewport`는 WebView2 자식 표면에 용량을 확보하고 실제 클라이언트 영역을 자른다. 네이티브 호스트는 진행 중인 크기 전달과 대기 중 최신 크기 하나를 관리한다. 문서는 전달받은 클라이언트 크기를 컨테이너에 적용한다. 갤러리는 같은 열 구성의 위젯을 재배치하고 방문한 예제 상태를 재사용한다.
- 왼쪽 위 드래그에서 같은 DXGI 프레임의 제목 표시줄은 고정돼도 앱 아이콘과 WebView2 자식 창은 약 한 입력 단계 움직였다. 최종 호스트는 `WM_NCCALCSIZE`에서 겹치는 유효 영역을 지정하고 자식 창의 마지막 물리 픽셀 이동을 합성기에 전달한다. 가로 오프셋이 바뀌면 `DwmFlush`로 직전 합성을 기다린다. CanvasKit은 표시 캔버스의 가로 원점을 유지하고 프레임마다 해당 세대의 오프셋을 적용한다. [브라우저 표면](../../../../Nelyx/sdk/src/frontend/dom/surface.tsx) · [CanvasKit 표면](../../../../Nelyx/skia/packages/web/src/surface.ts)

## 당시 검증

- Chrome은 크기만 변경한 부모, 분수 DPR, 워커의 이전 프레임 폐기와 복구, 별도 팝업을 확인했다. 기존 Demo Windows 패키지는 WebView2 빌드 ID·내장 자산·Rust IPC·클립보드·딥링크, 창 복원과 네이티브 클릭을 확인했다.
- 11-27 최종 Testbed 3 패키지 `4377e8e4a09d`에서 200% 배율, 1690·2024·2300px 시작 너비, 일반·Acrylic, 세 렌더 모드와 열 전환을 포함해 60Hz 가상 마우스 드래그를 측정했다. 왼쪽 위 드래그의 DXGI 합성 화면 1,752장에서 기준 아이콘 간 최대 오차는 가로 1px·세로 0px였고 앱 아이콘만 3px 이상 움직인 경우는 0회였다.
- 본문 표시 갱신은 1690px 왼쪽 위에서 초당 59.4회, 2300px에서 55.6회, 1열↔2열 전환에서 49.9회였다. 열 전환 중 최대 공백은 67.6ms였다. 이 수치는 Windows 합성 화면과 프로그램이 보낸 입력을 대상으로 했다.
- Esc로 드래그를 취소했을 때 좌표·DOM 크기 복원, 창 상태 전환, 갤러리·모달·iframe·입력값 보존을 확인했다. Testbed 3 타입 검사·Web 빌드와 루트·하위 경로의 백엔드 검사도 통과했다. [Windows 패키지 검사](../../../../Nelyx/eng/check-tauri-windows.mjs)

중간 `PAUSED / PARTIAL` 시점 뒤 순간 이동을 수정했다. 오른쪽 모서리의 가로 추종, 열 전환 중 표시 공백과 물리 마우스 체감은 남았다. 최종 공유 호스트에서 Demo까지 포함한 정식 Windows 패키지 회귀의 통과 기록은 원문에 없다.

당시 Testbed 3 실행 명령은 저장소 루트의 `npm.cmd run deploy -- --platform windows --app Testbed3`다.
